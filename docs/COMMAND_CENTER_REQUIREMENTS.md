# 4. РАЗДЕЛ №1 — ДАШБОРД

**Маршрут:** `/dashboard`

## Назначение

Главная рабочая панель гильдии.

Пользователь должен за несколько секунд понять:

- Сколько золота имеется.
- Какие активности проходят.
- Какова посещаемость.
- Кто наиболее активен.
- Сколько начислено и выплачено.
- Когда следующая выплата.
- Какие события требуют внимания.

Это обзорная страница, а не копия полной статистики.

## 4.1. Верхний блок

Создай атмосферный Hero-блок:

- Логотип XD.
- Название гильдии.
- Фоновое изображение в японском фэнтези-стиле.
- Текущий расчётный период.
- Краткая информация о состоянии гильдии.

Используй существующие графические ресурсы проекта, если они подходят.

Текст и показатели должны хорошо читаться поверх изображения.

## 4.2. Основные показатели

Отобрази карточки:

**Карточка 1. Казна Прайма**

- Текущий доступный фонд.
- Количество золота.
- Подпись «70% — фонд зарплат».
- Переход к операциям казны.

**Карточка 2. Казна Мини-РБ**

- Текущий фонд.
- Количество золота.
- Подпись «100% — фонд зарплат».

**Карточка 3. Казна гильдии**

- Резерв гильдии.
- Доступный баланс.
- Изменение за выбранный период.

**Карточка 4. Дроп**

- Стоимость дропа Прайма.
- Стоимость дропа Мини-РБ.
- Стоимость непроданного имущества.

**Карточка 5. Посещаемость**

- Среднее количество участников.
- Количество состоявшихся активностей.
- Изменение относительно предыдущего сопоставимого периода.

**Карточка 6. Выплаты**

- Начислено.
- Выплачено.
- Остаток задолженности.

**Карточка 7. Ближайшая выплата**

- Дата выплаты.
- Оставшиеся дни.
- Текущий расчётный период.

Все значения должны вычисляться из реальной базы данных.

Если сравнение с предыдущим периодом невозможно, показывай «Нет данных», а не выдуманный процент.

## 4.3. Графики

Создай три интерактивных графика:

1. Динамика казны.
2. Посещаемость участников.
3. Доходы и расходы.

Функции:

- Выбор периода.
- Подсказки при наведении.
- Легенда.
- Адаптивное отображение.
- Скрытие отдельных рядов данных.
- Переход к подробной статистике.

## 4.4. Рейтинги

Два отдельных блока:

- ТОП-5 участников Прайма.
- ТОП-5 участников Мини-РБ.

Отображай:

- Место.
- Игровой ник.
- Класс.
- Процент посещаемости.
- Индикатор активности.

Нажатие на игрока открывает его профиль.

## 4.5. Активности

Отобрази:

- Ближайшие запланированные события.
- Последние пять состоявшихся событий.
- Название.
- Дату.
- Количество участников.
- Статус.
- Баннер, если имеется.

Разделяй запланированные события и фактически проведённые активности. Запись на предстоящее событие сама по себе не должна увеличивать подтверждённую посещаемость.

## 4.6. Настройка дашборда

Пользователь может:

- Изменять расположение панелей.
- Менять ширину и высоту.
- Скрывать необязательные блоки.
- Возвращать расположение по умолчанию.

Сохраняй настройки в браузере или профиле пользователя, если такая инфраструктура уже существует.

На мобильных устройствах используй надёжное сенсорное управление.

# 5. РАЗДЕЛ №2 — СТАТИСТИКА

**Предлагаемый маршрут:** `/statistics`

## Назначение

Полноценный аналитический центр гильдии.

Важно: в текущем проекте маршрут `/dashboard` используется как статистический обзор. Сохрани его, а подробную аналитику выдели в отдельный раздел.

Не создавай две одинаковые страницы.

## 5.1. Фильтрация

Добавь переключатели:

- Текущий расчётный период.
- Предыдущий расчётный период.
- Последние 7 дней.
- Последние 30 дней.
- Произвольный диапазон.
- Архивные периоды.

Пользователь выбирает категорию:

- Все активности.
- Прайм.
- Мини-РБ.
- PvE.
- PvP.

Фильтры должны согласованно влиять на соответствующие графики и таблицы.

## 5.2. Общая аналитика

Показывай:

- Всего участников.
- Количество проведённых активностей.
- Среднюю посещаемость.
- Количество участий.
- Количество PvP-активностей.
- Посещаемость Прайма.
- Посещаемость Мини-РБ.
- Динамику активности гильдии.

Разделяй количество уникальных игроков и суммарное количество участий.

## 5.3. Посещаемость

Графики:

- Посещаемость по дням.
- Посещаемость по неделям.
- Активность отдельных игроков.
- Сравнение Прайма и Мини-РБ.
- Динамика за выбранные периоды.

Таблица игроков:

| Показатель | Назначение |
|---|---|
| Игрок | Ник персонажа |
| Класс | Игровая роль |
| Всего активностей | Количество доступных событий |
| Посещено | Фактические участия |
| Общая посещаемость | Процент |
| Прайм | Взвешенный процент |
| Мини-РБ | Процент посещаемости |
| PvP | Количество участий |

Расчёт общей посещаемости:

`посещённые активности / все учитываемые активности × 100%`

Для Прайма используй существующую взвешенную модель.

Не подменяй её простым количеством походов.

Сохрани общие расчётные функции:

- `src/lib/attendance.ts`
- `src/lib/activityWeights.ts`

## 5.4. PvP-аналитика

Создай отдельную вкладку:

- Количество PvP-событий.
- Количество PvP-участий.
- Убийства игроков.
- Очки чести.
- Победы и поражения, если они подтверждены.
- Лидеры PvP.
- Динамика по времени.

Используй существующие поля активности и участника.

Не рассчитывай победу из факта присутствия.

## 5.5. Финансовая статистика

Показывай:

- Доход Прайма.
- Доход Мини-РБ.
- Долю гильдии.
- Проданный дроп.
- Текущие остатки.
- Начисленные зарплаты.
- Фактические выплаты.
- Задолженность.
- Изменения по периодам.

Предусмотри графики и таблицы для сопоставления.

## 5.6. Рейтинг игроков

Отдельные рейтинги:

- По общей посещаемости.
- По Прайму.
- По Мини-РБ.
- По PvP.
- По начислениям.
- По количеству активностей.

Сортировка должна выполняться по фактическим числовым значениям.

## 5.7. Экспорт

Предусмотри CSV-экспорт доступных пользователю аналитических данных.

Проверяй права на сервере.

Не экспортируй секреты, пароли, токены и служебные идентификаторы авторизации.

При экспорте обеспечь защиту от формульных инъекций в CSV.

# 6. РАЗДЕЛ №3 — АКТИВНОСТИ

**Маршруты:**

- `/activities`
- `/activities/[id]`

## Назначение

Управление мероприятиями гильдии и учёт фактического участия игроков.

## 6.1. Основной экран

В верхней части:

- Общее количество активностей.
- Среднее число участников.
- Максимальное число участников.
- Количество отменённых мероприятий.

Ниже — панель фильтрации.

Фильтры:

- Дата начала.
- Дата окончания.
- Название активности.
- Категория.
- PvE/PvP.
- Статус.
- Участник.

Добавь поиск, сортировку, сброс фильтров и серверную пагинацию.

## 6.2. Карточка активности

Каждая карточка содержит:

- Баннер.
- Название.
- Дату и время.
- Категорию.
- Режим PvE/PvP.
- Сложность.
- Статус.
- Количество участников.
- Коэффициент посещаемости.
- Переход к деталям.

Поддержи изображения и видео, если формат уже используется в проекте.

Медиафайлы загружай отдельными HTTP-запросами. Не передавай крупные файлы через сериализованные свойства React-компонентов.

## 6.3. Создание активности

Поля формы:

- Название.
- Дата.
- Время, если предусмотрено моделью.
- Категория: Прайм или Мини-РБ.
- Режим: PvE или PvP.
- Сложность: обычная или героическая.
- Дневная/ночная активность.
- Коэффициент посещаемости.
- Состав участников.
- Гостевые участники.
- Скриншоты состава.
- Скриншоты дропа.

Разреши поиск и множественный выбор участников.

Предотвращай повторное добавление одного игрока в одну активность.

Валидируй все поля на сервере.

## 6.4. Коэффициенты посещаемости

Сохрани существующую механику коэффициентов.

Примеры действующих значений:

- АГЛ — 0,5.
- АГЛ Т2 — 1.
- Авиара — 0,75.
- Разъярённый Левиафан — 1,5.
- PvP — 1.

Полную таблицу бери из `activityWeights.ts`.

Не заменяй её сокращённым списком.

В существующей модели для посещаемости АГЛ, АГЛ Т2 и Кошка относятся к Мини-РБ, PvP — к Прайму.

Категория финансовой операции и категория учёта посещаемости не должны ошибочно подменять друг друга.

## 6.5. Детальная страница

Внутри активности:

**Общая информация**

- Основные характеристики.
- Дата.
- Статус.
- Организатор.
- Руководитель рейда.

**Состав рейда**

- Список участников.
- Игровые роли.
- Факт участия.
- Полное участие.
- Гостевые участники.

**PvP**

- Убийства.
- Очки чести.
- Результат сражения.
- Подтверждение результата.

**Дроп**

- Полученные предметы.
- Количество.
- Стоимость.
- Категория.
- Склад назначения.
- Связь с реестром дропа.

**Подтверждения**

- Скриншоты.
- Подтверждение убийства босса.
- Подтверждение других достижений, если они предусмотрены существующей моделью.

Нельзя автоматически считать участие доказательством убийства босса или победы в PvP.

## 6.6. Редактирование

Реализуй:

- Создание.
- Редактирование.
- Отмену.
- Изменение состава.
- Управление скриншотами.
- Изменение привязанного дропа.

Для удаления используй подтверждение и проверку зависимостей.

Не удаляй финансовую историю каскадно без анализа последствий.

## 6.7. Связи

После изменения подтверждённой активности должны корректно обновляться:

- Посещаемость.
- Статистика игрока.
- Рейтинги.
- Зарплатные расчёты.
- Дашборд.

### Правила распределения

Сохрани действующую модель:

**Прайм**

70% поступлений — фонд зарплат.

30% поступлений — казна гильдии.

**Мини-РБ**

100% поступлений — фонд зарплат Мини-РБ.

Не перечисляй 30% поступлений Мини-РБ в резерв гильдии.

Пример:

Продажа Прайма за 100 000 золота:

- 70 000 — фонд Прайма.
- 30 000 — казна гильдии.

Продажа Мини-РБ за 100 000 золота:

- 100 000 — фонд Мини-РБ.
- 0 — казна гильдии.

Смешанные продажи распределяй по существующему алгоритму пропорционально стоимости позиций, не учитывая одну продажу дважды.

## 8.2. Инвентарь

Создай интерфейс трёх складов:

1. Общий инвентарь.
2. Инвентарь ХД.
3. Инвентарь НТ.

Для каждого предмета:

- Название.

- Количество.
- Цена единицы.
- Суммарная стоимость.
- Источник получения.
- Дата.
- Категория.
- Статус продажи.

Функции:

- Добавление предмета.
- Изменение разрешённых характеристик.
- Перемещение между складами.
- Частичное перемещение.
- Частичная продажа.
- Полная продажа.
- История операций.

Права операций должны соответствовать существующим правилам проекта.

При перемещении предметов между складами не создавай фиктивный доход.

При частичной продаже не списывай весь остаток.

## 8.3. Продажа дропа

При продаже:

1. Выбрать склад.
2. Выбрать предмет.
3. Указать количество.
4. Указать сумму сделки.
5. Проверить доступный остаток.
6. Подтвердить операцию.
7. Уменьшить складской остаток.
8. Создать связанную финансовую запись.
9. Пересчитать казну.
10. Обновить дашборд и статистику.

Изменение склада и создание финансовой операции выполняй атомарно.

Не допускай повторной обработки одного запроса после сетевого сбоя.

При отмене операции используй контролируемую компенсацию и журнал действий.

## 8.4. Зарплаты игроков

Распределяй зарплатные фонды по фактической посещаемости.

Учитывай:

- Категорию.
- Взвешенную посещаемость Прайма.
- Посещаемость Мини-РБ.
- Индивидуальный коэффициент игрока.
- Минимальный порог посещаемости 20%.

Игрок с посещаемостью ниже 20% по соответствующей категории не получает долю этого фонда.

Доли остальных игроков перераспределяются пропорционально.

Сохрани существующий алгоритм метода наибольшего остатка для целочисленного распределения золота.

Используй общие реализации:

- `src/lib/salary.ts`
- `src/lib/proportionalSplit.ts`

Сумма распределённых долей должна в точности соответствовать распределяемому фонду, когда существуют игроки, имеющие право на выплаты.

Не распределяй фонд искусственно, когда нет ни одного подходящего получателя.

## 8.5. Выплаты

На `/payments` реализуй:

- Выбор периода.
- Список получателей.
- Начисления Прайма.
- Начисления Мини-РБ.
- Общую сумму.
- Статус выплаты.
- Дату выплаты.
- Историю.
- Остаток.

Статусы:

- Ожидает.
- Выплачено.

Отмена выплаты должна формировать корректную обратную операцию и восстанавливать нужный фонд.

Исключи двойные выплаты.

Ключевое требование:

**Выплата одному игроку не должна уменьшать ранее рассчитанную долю остальных игроков.**

Для этого используй исходный фонд периода, учитывая уже произведённые выплаты, а не рассчитывай все доли от текущего остатка.

## 8.6. Периоды и архив

Расчётный период гильдии:

Не смешивай живой баланс с архивным.
