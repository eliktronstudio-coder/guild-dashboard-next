## Сохранённые правила и инфраструктура

- Next.js 16 / React 19 / TypeScript / Tailwind / Prisma / SQLite; существующая авторизация сохранена.
- Маршруты `/dashboard`, `/activities`, `/activities/[id]`, `/players`, `/players/[id]`, `/treasury`, `/payments`, `/archive` сохранены.
- Полная таблица `activityWeights.ts`, раздельная категория посещаемости и финансов, метод наибольшего остатка, порог 20%, коэффициенты 0–1,25, правила фондов Прайм 70/30 и Мини-РБ 100% сохранены.
- Исходный фонд включает уже произведённые выплаты: выплата одному игроку не уменьшает доли остальных.
- Снимки архива не пересчитываются при переименовании/удалении профиля.
- Существующие достижения, дизайн-редактор, правила торгов, калькуляторы и бот сохранены. Удаление лота аукциона теперь использует ту же компенсирующую операцию казны и сохраняет исходную денежную запись.
- Не выполнялись reset, seed рабочей базы, удаление пользовательских данных, слияние или автоматический деплой.

## Общая архитектура

`access.ts` проверяет подтверждённую роль в серверном entry point страницы и API до выборки закрытых данных. Гости и `random` получают страницу входа/ожидания; CSS-размытие не используется как граница доступа. При потоковом SSR ответ с redirect может иметь HTTP 200, но закрытого содержимого в HTML/RSC нет.

`statistics.ts` использует существующие `attendance.ts`, `salary.ts`, `queries.ts`; большие наборы не передаются в браузер для фильтрации. Состав и рейтинги сортируются на сервере; клиент получает страницу из 25 строк. Для сортировки по вычисляемой посещаемости сервер пока читает состав целиком — это не SQL-пагинация вычисляемых показателей. Для существенно большей гильдии потребуется профилирование и агрегирование на SQL-стороне.

`ReportFilters`, `Pagination`, `AnalyticsChart` переиспользуются в аналитике и составе; старые `StatCard`, `DashboardPanel`, `SectionHeader`, `EmptyState`, `ActivityRow` и общий layout сохранены. Добавлены общие loading/error состояния, фокус клавиатуры и reduced motion. Светлая тема включает фон боковой панели.

Персональные начисления доступны владельцу и admin/gm. Общий финансовый журнал гильдии остаётся доступным подтверждённым участникам в рамках существующей политики; РЛ не получает права на финансовые изменения. Экспорт исключает auth-идентификаторы, токены и пароли и защищает ячейки CSV от формул.

`AppSetting` используется только для технической блокировки, окна попыток входа и квитанции повторного запроса продажи (хеш запроса + id операции). Альтернативных сущностей казны/посещаемости не создавалось. Сохраняются ранее существовавшие пользовательские настройки.

## Миграция

`20261109000100_treasury_reversals` добавляет nullable `TreasuryTransaction.reversalOfId` и уникальный индекс. Существующие суммы/строки не меняются. Перед рабочей публикацией требуется согласованная резервная копия SQLite и штатное `prisma migrate deploy`; на рабочем сервере миграция не выполнялась.

Отмена продажи создаёт одну компенсирующую операцию и возвращает связанный дроп той же транзакцией. При наличии неотменённых выплат отмена дохода блокируется: сначала нужно отменить выплаты. Оригинальная денежная запись остаётся в журнале. Откат приложения не отменяет проведённые финансовые операции.

## Проверки и границы готовности

Полные результаты зафиксированы в `COMMAND_CENTER_VALIDATION.md`. Тесты работают с временными SQLite-файлами; browser/HTTP-проверка сама создаёт и удаляет изолированный стенд. Тестовые имена и цифры не используются как fallback в приложении.

Сохраняются ограничения:

- Точная серверная версия и реальная база не проверены; приёмка production и восстановление настоящей резервной копии не выполнены.
- В старом дизайн-редакторе и вспомогательных калькуляторах есть исходные ошибки полного ESLint. Изменённые application-модули проверяются отдельно; эти ошибки не скрыты настройками lint.
- Не добавлена новая система деактивации игроков: удаление имеющего историю игрока блокируется. Привязка и редактирование сохраняются; для полноценного статуса бывшего участника нужен отдельный согласованный шаг модели данных.
- Нет гарантии уникальности никнеймов для прямых SQL-записей или сторонних старых ботов: существующая схема не имеет нормализованного уникального имени. Новые нормализованные дубли проверяются в веб-формах. Перед индексом нужно проверить существующие дубли без их удаления.
- В журнале казны добавлены серверные страницы и фильтры, CSV финансовых операций. Экспорт не является резервной копией всей базы или медиа.
- Проверены выбранные пользовательские сценарии, а не каждая кнопка старого дизайн-редактора, калькулятора и бота.

## Публикация отдельным действием

1. Установить, какой репозиторий и каталог действительно обслуживает нужный домен; получить commit, `WorkingDirectory` сервиса и путь `DATABASE_URL` без раскрытия секретов.
2. Проверить HTTPS на выбранном домене. В production cookie теперь всегда Secure, поэтому вход по старому HTTP-адресу не является поддерживаемой конфигурацией.
3. Создать согласованную копию SQLite вместе с WAL/SHM средствами SQLite backup API, проверить восстановление в отдельный файл. Не копировать только основной файл во время записи.
4. После отдельного разрешения применить добавочную миграцию и установить проверенную версию с возможностью возврата приложения.
5. Пройти живую приёмку admin/gm/rl/member/random, продажу/отмену/выплату на согласованных тестовых данных, проверить архив и запрет закрытых API.

Полное пользовательское ТЗ сохранено в `COMMAND_CENTER_REQUIREMENTS.md`; эти ограничения не выдаются за реализованные функции.
